# 用户指南

## 模块与功能概述

OpenAN 知识服务（Knowledge Service）提供文档知识库与图谱知识库、检索流程编排，以及基于知识库的问答能力。项目包含 Knowledge Studio 前端和 FastAPI 后端，PostgreSQL（pgvector）存储业务数据与向量，OpenSearch 提供关键词检索。

当运维或开发团队需要基于自有文档构建可验证的共享知识库，并且需要检查检索结果、把检索能力编排成流程、通过 REST 接口供智能体或应用复用时，使用本服务。

### 使用场景

- 基于产品手册、维护记录或标准规范构建文档知识库，为问题检索相关片段。
- 基于领域本体构建图谱知识库，从文档抽取实体与关系，回答需要沿关系遍历的问题。
- 将关键词、向量、图谱检索编排成检索流程，发布后由智能体或下游系统通过 `POST /query` 调用。
- 登记并测试模型端点（LLM、Embedding、Reranker），使文档入库和答案生成使用部署方选定的模型服务。

### 功能清单

| 工作区 | 默认入口 | 能力 |
| --- | --- | --- |
| 文档知识库 | `/#/knowledge` | 创建知识库和目录，导入并处理文档，查看切片，下载原文，重试失败文档 |
| 图谱知识库 | `/#/graph` | 管理本体模板，从文档抽取或导入图谱，查询、可视化、编辑和导出实体与关系 |
| 知识检索 | `/#/flow` | 在画布上编排关键词、向量或图谱检索，保存草稿、校验、发布与取消发布 |
| 对话测试 | `/#/chat` | 选择已发布的检索流程，流式查看回答、检索证据和引用 |
| 模型管理 | `/#/models` | 登记、启停和测试 LLM、Embedding 与 Reranker，按需设置默认模型 |

### 基本概念

| 概念 | 说明 |
| --- | --- |
| 知识库 | 文档或图谱数据的容器。`POST /knowledge-bases` 默认创建文档知识库，`?type=graph` 创建图谱知识库 |
| 目录 | 知识库内用于组织文档的文件夹 |
| 文档 | 导入知识库的 Markdown、TXT、DOCX 等文件。每个文档有处理状态，失败的文档可重新处理，无需重新上传原件 |
| 切片 | 文档切分产生的片段。切片经向量化和索引写入，检索命中后作为证据返回 |
| 算子 | 文档入库和流程编排中使用的处理步骤，通过 `/operators` 系列接口查询和配置 |
| 检索流程 | 由检索节点组成的画布配置。流程保存为草稿，校验后发布；只有已发布的流程才能被对话测试选用 |
| 查询追踪 | 一次查询的执行记录，包含检索证据和耗时，可通过 `/query-traces` 读取 |
| 模型 | 在模型管理中登记的 LLM、Embedding 或 Reranker 端点。后端使用 `RKB_SECRET_KEY` 加密凭据 |

### 工作原理

文档入库依次经过解析、切分、向量化和索引写入四个阶段。全部阶段成功，文档才变为可用状态。向量化使用知识库配置的 Embedding 模型，关键词索引写入 OpenSearch。

检索支持三种模式：面向切片的向量检索、面向 OpenSearch 索引的关键词检索，以及先通过向量相似度找到种子节点、再按深度沿关系传播的图谱检索。`POST /retrieval` 直接执行文档检索，`POST /knowledge-bases/{kbase_id}/graph/query` 执行图谱检索。

问答执行已发布的检索流程。`POST /query` 接收 `workflow_id` 和 `conversation_id`；`stream` 为 `true` 时以 Server-Sent Events 返回答案，检索证据和引用一并包含在流中。

## 安装

### 前置条件

- Linux 主机，安装 Docker Engine 和支持 `up --wait` 的 Docker Compose v2
- 使用 `curl` 做健康检查
- 仓库检出包含 `backend/`、`frontend/` 和 `deploy/docker-compose.yml`
- 首次构建可访问镜像仓库、PyPI 和 npm，或在环境文件中配置可用的镜像源
- 宿主机端口 `8080`（Web）和 `8091`（后端）未被占用
- Linux 上 OpenSearch 需要 `vm.max_map_count` 至少为 `262144`

### 快速开始

以下命令在部署主机的仓库根目录执行。

1. 检查部署环境。

   ```bash
   docker version
   docker compose version
   ```

2. 准备环境文件。复制示例，填入 `POSTGRES_PASSWORD`、`RKB_DB_PASSWORD` 和 `RKB_SECRET_KEY`。

   ```bash
   (
     umask 077
     cp -n deploy/.env.example deploy/.env
   )
   ```

   Agent 或 CI 做首次安装时，可用 OpenSSL 自动生成三个必填值。下面的命令仅在环境文件不存在时创建它；已有部署沿用原来的环境文件、Compose 项目名和数据卷。

   ```bash
   if [ ! -e deploy/.env ]; then
     (
       set -euC
       umask 077
       studio_pg_password="$(openssl rand -hex 24)"
       studio_app_password="$(openssl rand -hex 24)"
       studio_secret_key="$(openssl rand -hex 32)"
       printf 'POSTGRES_PASSWORD=%s\nRKB_DB_PASSWORD=%s\nRKB_SECRET_KEY=%s\n' \
         "$studio_pg_password" "$studio_app_password" "$studio_secret_key" > deploy/.env
     )
   fi
   ```

3. 启动并检查服务。

   ```bash
   docker compose --env-file deploy/.env -f deploy/docker-compose.yml config --quiet
   docker compose --env-file deploy/.env -f deploy/docker-compose.yml up -d --build --wait
   docker compose --env-file deploy/.env -f deploy/docker-compose.yml ps

   curl -fsSL --retry 5 --retry-connrefused -o /dev/null http://localhost:8080/
   curl -fsS --retry 5 --retry-connrefused http://localhost:8091/api/knowledge-service/v1/health
   curl -fsS --retry 5 --retry-connrefused http://localhost:8080/api/knowledge-service/v1/health
   ```

   对外部署时，将 HTTPS 反向代理指向 Web 端口。Web 会将同域的 API 请求转发到后端。上层代理转发 `POST /api/knowledge-service/v1/query` 时应关闭响应缓冲，以便逐段显示 SSE 回答。

4. 登录并验收。打开 `http://localhost:8080/#/knowledge`，远程部署使用目标服务器的 Web 地址。默认管理员用户名为 `admin`。新数据库初始化时，若 `RKB_ADMIN_PASSWORD` 留空，服务会生成随机初始密码，可在部署主机读取：

   ```bash
   docker compose --env-file deploy/.env -f deploy/docker-compose.yml \
     exec backend cat /data/rkb/initial-admin-password
   ```

   首次登录后按界面提示改密，改密成功后密码文件自动删除。如果设置了 `RKB_ADMIN_PASSWORD`，首次登录使用该配置值；已有数据库继续使用其中的账号。

   按以下两项验收部署结果：Compose 四个服务正常运行，Web 首页可访问，直连和 Web 代理的健康检查均返回 `ok`；随后使用真实模型完成一次文档导入，确认文档状态为可用，且能检索到该文档的切片。

## 使用

### 前置条件

- 部署已运行，管理员密码已完成修改
- 至少一个 Embedding 模型端点可从后端容器访问；生成回答还需要可用的 LLM 端点

### 登记模型

1. 打开 `/#/models`，添加 Embedding 端点，填写基础地址、服务商的模型标识、向量维度和凭据。
2. 测试连通性。要生成回答，再添加并测试 LLM；流程包含重排节点时，再配置 Reranker。

### 创建知识库并导入文档

1. 打开 `/#/knowledge`，新建知识库，选择已登记的 Embedding 模型。
2. 打开文档页，导入一份含文字的 Markdown、TXT 或 DOCX 文件。
3. 等待文档状态变为可用，查看切片数及内容。处理失败时，在文档操作菜单选择重新处理，无需重新上传原件。

### 构建图谱知识库

1. 通过 `POST /knowledge-bases?type=graph` 创建图谱知识库，或打开 `/#/graph` 图谱工作区。
2. 通过图谱模板页面管理本体模板：创建、更新、导入和删除模板。
3. 对文档提交图谱抽取，或导入已有图谱。
4. 查询、可视化、编辑和导出实体与关系。导出的图谱可用于归档或迁移到其他环境。

### 编排并发布检索流程

1. 打开 `/#/flow`，新建流程，将检索节点绑定到目标知识库。
2. 按所选节点配置 Embedding 或生成模型。
3. 保存并校验流程，在列表中发布。修改已发布的流程后，保存只更新草稿，重新发布才会让新配置生效。

### 对话验证

1. 打开 `/#/chat`，选择已发布的流程。
2. 提问并查看流式回答、检索证据和引用。

### 通过 API 验证检索

所有路径均相对于 `/api/knowledge-service/v1`。可直接连接 `http://localhost:8091`，或使用 Web 同域代理 `http://localhost:8080`。默认 `AUTH_MODE=local` 下，请用已完成首登改密的账号登录。登录返回 HttpOnly 会话 Cookie `openan_session`。持会话发起业务 `POST`、`PUT`、`PATCH`、`DELETE` 请求时，`Origin` 或 `Referer` 的主机和端口必须与请求地址匹配。

```bash
studio=http://localhost:8080
api="$studio/api/knowledge-service/v1"
cookies="$(mktemp)"
trap 'rm -f "$cookies"' EXIT

read -rsp '管理员密码: ' studio_password
printf '\n'
printf '%s' "$studio_password" |
  python3 -c 'import json, sys; print(json.dumps({"username": "admin", "password": sys.stdin.read()}))' |
  curl -fsS -c "$cookies" -H 'Content-Type: application/json' \
    --data-binary @- "$api/auth/login"
unset studio_password

curl -fsS -b "$cookies" "$api/knowledge-bases"

curl -fsS -b "$cookies" -H "Origin: $studio" -H 'Content-Type: application/json' \
  --data-binary @- "$api/retrieval" <<'JSON'
{
  "question": "测试环境的归档周期是多少？",
  "model": "<已登记的 Embedding 模型名>",
  "type": 0,
  "bases": [{"baseList": ["doc_<知识库 ID>"], "priority": 0, "top_k": 3}]
}
JSON
```

`type: 0` 是向量检索，改用 `type: 1` 可检查关键词命中。`doc_` 是文档检索所用的前缀，知识库列表接口返回的 `id` 本身不含这个前缀。响应按库返回 `baseName` 和 `docs`，其中 `docs` 是命中的片段。

## 管理

### 认证模式

| `AUTH_MODE` | 行为 |
| --- | --- |
| `local` | 默认。本地账号，会话 Cookie |
| `none` | 关闭本地鉴权 |
| `gateway` | 由受信任的前置网关验证身份并处理身份头 |

### 配置参考

完整配置见 [deploy/docker-compose.yml](../../deploy/docker-compose.yml) 和 [deploy/.env.example](../../deploy/.env.example)。

| 变量 | 用途 |
| --- | --- |
| `POSTGRES_PASSWORD`、`RKB_DB_PASSWORD` | 必填。分别是数据库管理员和应用数据库角色的口令 |
| `RKB_SECRET_KEY` | 必填。用于加密模型凭据。恢复既有数据库时须保留对应密钥 |
| `RKB_ADMIN_USERNAME`、`RKB_ADMIN_PASSWORD` | 新数据库的管理员账号配置。用户名默认 `admin`，密码可留空以自动生成 |
| `AUTH_MODE` | 默认 `local`。`none` 关闭本地鉴权，`gateway` 依赖受信任的前置网关 |
| `WEB_PORT`、`KNOWLEDGE_BASE_PORT` | 宿主机端口，默认分别为 `8080` 和 `8091` |
| `WEB_BASE_URL` | Web 构建路径，默认 `/`。改为子路径时需重新构建 Web |
| `EMBEDDING_MODEL`、`EMBEDDING_DIMENSION` | 向量模型及维度的部署级默认值。配置名称和维度本身不会启动模型端点 |
| `MODEL_GATEWAY_URL`、`GENERATION_GATEWAY_URL`、`RERANK_URL` | 可选。预配置 Embedding、LLM、Reranker 端点，也可以在模型管理中登记 |
| `RKB_STORAGE_BACKEND` | 默认 `local`，知识库文件写入 `/data/kb` |

默认 Compose 数据卷为 `pgdata`（业务数据与向量）、`osdata`（搜索索引）、`kbdata`（知识库文件）和 `rkbdata`（日志及其他运行文件）。普通 `docker compose down` 保留数据卷，附加 `-v` 会删除数据卷。

### 常见问题

| 现象 | 检查方法 |
| --- | --- |
| OpenSearch 启动失败 | 在运行 Docker 的 Linux 主机检查 `vm.max_map_count`。若低于 `262144`，可用 `sudo sysctl -w vm.max_map_count=262144` 临时调整 |
| 首登后 API 返回 `403 password_change_required` | 先在页面完成改密，再用新密码登录获取会话 |
| API 返回 `403 csrf_rejected` | 确认 `Origin` 或 `Referer` 与实际请求的地址匹配 |
| 文档显示向量化失败 | 核对知识库选用的模型、端点、凭据和向量维度，再重新处理 |
| 对话测试找不到流程，或仍使用旧配置 | 从知识检索发布流程；更新草稿后重新发布 |
| 需要查看处理日志 | 执行 `docker compose --env-file deploy/.env -f deploy/docker-compose.yml logs -f backend` |
